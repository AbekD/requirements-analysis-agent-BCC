# Агент проверки качества требований (MVP)

ИИ-агент выполняет **статическое ревью** готового документа с требованиями до начала разработки: нарезает документ
на отдельные требования, оценивает каждое по критериям качества, проверяет набор требований целиком
(противоречия, дубли, расхождения между основной и дочерней спецификациями, пробелы) и формирует отчёт
на русском языке в формате Markdown. Это анализ формулировок, а не запуск тестов программы.

Критерии взяты из ISO/IEC/IEEE 29148:2018 (п. 5.2.5, 5.2.6) и IEEE Std 830-1998 (п. 4.3).
Формальное соответствие стандартам не заявляется.

## Архитектура

```
src/
├── main.py                    CLI, коды возврата
├── config.py                  .env, модель по умолчанию (единственное место), версия агента
├── ingestion/
│   ├── parser.py              MD / TXT / PDF → строки + заголовки + номера строк (и страниц для PDF)
│   └── extractor.py           гибридное извлечение: детерминированная нарезка + классификация LLM
├── analysis/
│   ├── llm_client.py          ЕДИНСТВЕННЫЙ модуль, говорящий с Gemini: ретраи, rate-limit, валидация JSON
│   ├── prompts.py             промпты и определения критериев
│   ├── individual.py          пакетная проверка требований (10 критериев на каждый пункт)
│   ├── arithmetic.py          проверка сумм в поддерживаемых примерах приёмки
│   ├── acceptance.py          формализуемые проверки приёмки, последовательностей и API-контракта
│   ├── cross_analysis.py      проверка набора целиком (с чанкованием) + полнота спецификации
│   ├── findings.py            сведение в уникальные замечания без двойного счёта, статистика
│   └── analyzer.py            оркестратор + итоговая оценка
├── validation/validator.py    проверка цитат, ссылок на ID и мест в документе
├── models/schemas.py          все Pydantic-модели (документ, ответы LLM, результаты)
└── reporting/report_generator.py   Markdown-отчёт (разделы 1–8 + приложение)
tests/                         pytest, без сети и без ключа (Gemini мокается)
```

Ключевые решения:

* **Ничего не теряется при извлечении.** Документ режется детерминированно на элементы (пункты списков, строки
  таблиц, блоки кода, абзацы). Каждый элемент получает ID `REQ-NNN`; ID из документа (например, `Ф-1`) сохраняются.
  LLM только уточняет *тип* элемента пакетами и **не переписывает текст**, поэтому цитаты всегда дословные.
  Явные требования (с собственным ID или в разделах функциональных/нефункциональных требований, данных, интеграции,
  критериев приёмки) LLM не может перевести в «контекст».
* **Доказательность.** Цитата проверяется внутри указанного требования или раздела. Для противоречия требуются
  две непересекающиеся привязки. Отчёт подставляет исходные строки со взятым из документа адресом. При ошибке
  проверки замечание остаётся потенциальным, а текст неподтверждённой цитаты скрывается.
* **Проверки приёмки.** Поддерживаемые примеры сложения в тенге пересчитываются кодом. Отдельная проверка ищет
  расхождения между правилом о месяце покупки и табличным примером на границе месяцев. Остальные сценарии оценивает LLM.
  Для явно сформулированных правил код дополнительно проверяет обход месячного лимита после смены порога,
  операции записи в методе GET и расхождение между правилом HTTP 400 и примером ошибки в разделе HTTP 200.
* **Проверка пропусков.** Агент ищет опровержение заявленных пропусков по всему документу, в том числе
  в соседних разделах и таблицах. Чтобы снять замечание, требуется подтверждённая цитата. При неполной
  информации пропуск остаётся потенциальным. Уже зарегистрированное противоречие приводится в разделе проверки набора.
* **Прослеживаемость и повторы.** Учитывается адрес элемента в структуре документа. Повторы одного замечания
  объединяются с сохранением ссылок на затронутые элементы.
* **Строгий JSON.** Все ответы LLM — структурированный вывод по Pydantic-схемам; невалидный ответ повторяется с
  описанием ошибки (до 2 повторов), затем анализ помечается неполным в отчёте (не пропадает молча).
* **Анализ набора не по кускам.** Если документ не помещается в бюджет, чанки анализируются по очереди, но каждый
  получает сжатый список *всех* остальных элементов, чтобы конфликты между чанками не терялись.
* **Вердикт учитывает подтверждённость.** Критичный подтверждённый дефект приводит к `NOT_READY`. Потенциальные
  замечания могут потребовать уточнения. Для `NOT_READY` нужен подтверждённый дефект высокой или критичной серьёзности.

## Технологии

Python 3.11+, `google-genai` (Gemini API), `pydantic`, `python-dotenv`, `PyMuPDF`, `argparse`, `pytest`.
Без LangChain и других агентных фреймворков.

## Установка

```bash
python3 --version                    # нужен 3.11 или новее
python3 -m venv .venv && source .venv/bin/activate     # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

## Ключ Gemini API

1. Откройте Google AI Studio: <https://aistudio.google.com/apikey> и войдите в Google-аккаунт.
2. Нажмите **Create API key** и скопируйте ключ (бесплатного тарифа достаточно).
3. Создайте файл конфигурации и вставьте ключ:

```bash
cp .env.example .env
# затем отредактируйте .env:
# GEMINI_API_KEY=ваш_ключ
# GEMINI_MODEL=имя_поддерживаемой_модели      (необязательно; модель по умолчанию задана в src/config.py)
# GEMINI_REQUESTS_PER_MINUTE=10               (необязательно; ограничитель частоты запросов)
```

`.env` внесён в `.gitignore` — ключ в репозиторий не попадёт. Модель можно задать и аргументом `--model`.

## Запуск

```bash
python -m src.main --input /путь/к/requirements.md --output reports/requirements_report.md
```

Скачайте [входной документ организаторов](https://github.com/BCC-HUB/ai-requirements-validator-task/blob/main/docs/requirements.md)
и передайте путь к скачанному файлу. Например, если файл лежит рядом с папкой репозитория:

```bash
python -m src.main --input ../organizer_requirements.md --output reports/requirements_report.md
```

Аргументы: `--input/-i` (обязателен), `--output/-o` (по умолчанию `reports/requirements_report.md`), `--model`,
`--language` (`ru`|`en` — язык пояснений LLM; каркас отчёта всегда русский), `--rpm` (запросов в минуту),
`--batch-size` (от 1 до 8, по умолчанию 4), `--verbose/-v`.

Для документов, которые помещаются в контекст индивидуальной проверки, один запрос охватывает до четырёх пунктов.
Каждый пункт получает отдельную оценку по десяти критериям. Если ответ пропустил или продублировал ID,
агент повторяет проверку этого пункта отдельно. Большие документы проверяются по одному пункту за запрос.
При ошибках 429/5xx агент ждёт и повторяет запрос с нарастающей паузой.

**Коды возврата:** `0` — анализ завершён полностью; `1` — анализ не выполнен; `2` — ошибка входных данных или
конфигурации (нет файла, формат не поддерживается, пустой документ, нет `GEMINI_API_KEY`); `3` — отчёт создан,
но часть проверок не выполнена (это отражено в «Паспорте прогона»).

## Поддерживаемые форматы

`.md`, `.txt` (UTF-8 или CP1251), `.pdf` (текстовый слой через PyMuPDF; заголовки определяются по размеру шрифта,
в источниках указываются страницы). DOCX в MVP не поддерживается; сканы PDF без текстового слоя не распознаются (OCR нет).

## Где отчёт

В файле, указанном в `--output` (по умолчанию `reports/requirements_report.md`). Состав: 1 — паспорт прогона,
2 — таблица извлечённых требований, 3 — индивидуальная проверка (10 критериев на требование), 4 — проверка набора
и полнота, 5 — сводка, 6 — критические дефекты, 7 — итоговая оценка, 8 — приоритетные рекомендации,
приложение — реестр замечаний.

## Тесты

```bash
python -m pytest -q
```

Тесты не требуют ключа и сети: ответы Gemini заменяются заглушкой. Покрыто: разбор MD/TXT/PDF, пустой файл и
неподдерживаемый формат, генерация и сохранение ID, проверка цитат, невалидный вывод LLM и повторы, rate-limit,
сквозной прогон с частичными сбоями, коды возврата CLI.

## Известные ограничения MVP

* Элемент = абзац / пункт списка / строка таблицы / блок кода. Составные требования (например, Ф-2 из нескольких
  предложений) не дробятся на подтребования; многосоставность выявляется критерием «Атомарность».
* Индивидуальные вызовы получают весь документ как контекст (если он ≤ 24 тыс. символов), иначе — оглавление и
  раздел требования; для очень больших документов межразделные связи ловит только проверка набора.
* Проверка цитат — нормализованное точное вхождение; перефразированная цитата будет отклонена (это намеренно).
  «Подтверждённый пропуск» в полноте опирается на цитату ближайшего текста, а не на цитату отсутствующего.
* Качество оценок зависит от модели; серьёзность и «подтверждённость» вне цитат — суждение LLM, которое агент
  лишь ограничивает правилами (но не заменяет экспертную проверку).
* PDF: структура (заголовки, таблицы) восстанавливается эвристически; таблицы PDF обрабатываются как текст.
* Нет кэша: повторный запуск повторяет все обращения к модели; нет OCR и DOCX; отчёт только в Markdown.
* Отчёт всегда формируется агентом по прогону; вручную дописывать его не нужно и нельзя (сдаётся результат запуска).
